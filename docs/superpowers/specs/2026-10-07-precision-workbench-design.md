### 观察到的设计问题

1. 初始状态的对话区和空方案区同时占据大量面积，主操作不够集中。
2. 六步流程、协作者链和重复状态说明同时出现，用户要反复阅读同一信息。
3. 多层容器边框、卡片和标题形成碎片感，缺少稳定的页面主次关系。
4. 工单状态标签和筛选控件有重复表达，可以合并为一套状态筛选。
5. 资源展示应区分“已记录的安排”与“经查询确认的可用性”，不能因为缺少安排就显示空闲。
6. “Leader/Partner、运行模式”等信息可以移入技术详情；业务区使用设备、人员、工具、方案和工单这些熟悉的词。

## 5. 四页设计

### 5.1 主协作

视觉稿：`output/imagegen/precision-workbench-20261007/01-collaboration.png`

- 中间是主要对话，右侧是当前检查摘要，比例约 64:36。
- 输入框固定在对话区域底部；消息历史独立滚动，不遮挡最后一条消息。
- 初始状态仅有简短引导与原有快捷入口，不占用整屏展示空方案。
- 多轮补充明确显示用户消息、补充问题和资源查询进度。
- 右侧按实际数据逐项出现设备、异常、时间、时长和技能；未知信息显示“待补充”。
- 简化进展为“补充信息—协调资源—确认执行”，详细调用过程在资源与审计页和技术详情中查看。
- 生成方案后出现“查看并确认方案”；确认前不出现已预留、已创建等完成态。
- 声音功能是“上传录音”的可选入口，沿用现有文件分析流程。

### 5.2 方案确认

视觉稿：`output/imagegen/precision-workbench-20261007/02-plan-confirmation.png`

- 主区域像检查单：设备与检查时间优先，随后是人员、技能、工具和配件。
- 右侧固定为确认区，清楚说明当前是待确认、查询失败或已创建。
- 唯一主要按钮“确认并创建工单”，保留修改安排和取消操作。
- 重复确认继续走现有幂等处理；不因视觉调整制造新的业务请求路径。
- 没有方案时展示紧凑空状态和“返回主协作”，不显示一整屏空字段。
- 已建单时展示已有工单入口，禁止沿用待确认按钮覆盖原工单。

### 5.3 工单中心

视觉稿：`output/imagegen/precision-workbench-20261007/03-work-orders.png`

- 左侧为工单表格，右侧为选中工单的详情与处理记录。
- 状态筛选只保留一套标签；设备筛选与刷新位于同一行。
- 工单编号、设备、检查时间、负责人、状态按固定列组织。
- 操作按现有工单状态开放，使用后端返回的真实状态，不由前端猜测可执行操作。
- “新建检查任务”返回主协作，仍经过方案确认流程。
- 详情中展示资源分配和真实处理轨迹，技术编号默认折叠。
- 没有记录时显示空状态，查询失败显示错误，不用空列表掩盖错误。

### 5.4 资源与审计

视觉稿：`output/imagegen/precision-workbench-20261007/04-resources-audit.png`

- 左侧为人员、工具与配件目录；右侧为当前任务的协作记录。
- 人员表格展示姓名、技能、已记录安排。无相应记录时写“暂无已记录安排”，不直接写“空闲”。
- 工具和配件展示后端返回的数量及已有预留，单位保持一致。
- 选中资源的细节通过展开行或相邻详情区域显示，不新增资源编辑能力。
- 协作记录以业务动词组织：补充信息、查询资源、确认方案、预留资源、创建工单。
- “调用记录”保留真实调用结果与错误；AIC、sessionId、taskId、messageId 和 JSON 默认放入技术详情。
- 当前没有选中任务时明确提示，不把其他历史任务的审计记录混入本次协作。

## 6. 数据绑定与不可变约束

| 内容 | 现有来源/路径 | 呈现约束 |
| --- | --- | --- |
| 设备、人员、库存、已有工单 | `/api/bootstrap` | 人名、设备编号和数量全部使用后端数据 |
| 会话与多轮消息 | `/api/conversations`、`/api/conversations/{sessionId}/messages` | 不为视觉切换重建任务；保留会话上下文 |
| 方案确认、取消与轨迹 | `/api/tasks/{taskId}/confirm`、`/cancel`、`/trace` | 人工确认门、幂等与补偿沿用现有逻辑 |
| 工单列表及处理动作 | `/api/work-orders`、`/{id}/status`、`/{id}/cancel` | 状态变化以响应为准，失败时不显示成功 |
| 调用记录 | `/api/aip-calls` | 缺少记录就显示缺少，不生成推测轨迹 |
| 服务状态 | `/api/agents/status` | 与平台验收状态分开；业务服务可用不代表平台验收已通过 |
| 声音辅助 | `/api/audio/analyze` | 只沿用现有上传与确认流程，不新增录音或部件诊断 |
| 人员已记录安排 | 工单已有的 `reservations` 与人员数据 | 没有记录不等于经资源 Partner 确认可用 |

不得把图中的 10 月 08 日、模拟人员、WO-示意 编号、库存或绿色状态写入正式页面的默认业务数据。当前“模拟业务数据”和“平台完整验收待完成”的性质应保留可见、清楚的表达。

## 7. 状态、交互与响应式

| 状态 | 用户看到什么 |
| --- | --- |
| 尚未开始 | 简短引导、可输入区域与可选上传入口 |
| 待补充 | 一个明确问题和已知设备/时间信息，不出现可确认方案 |
| 查询资源中 | 保留已知信息，当前步骤显示查询中；不反复闪烁整页 |
| 待确认 | 人员、时间、资源方案与唯一确认按钮 |
| 创建中 | 按钮禁用并标明正在创建；仍由后端保证重复请求安全 |
| 已创建 | 真实工单编号和结果，后续重复确认显示同一结果 |
| 已取消 | 展示取消结果及允许的下一步，不保留可误点的确认按钮 |
| 资源冲突 | 指明冲突和可修改项，沿用现有重新协调行为 |
| 网络/业务错误 | 保留输入与上下文，显示实际原因和现有重试入口 |
| 恢复中 | 先读取后端状态，再决定是否开放动作，避免把未知当成功 |

### 目标尺寸

- **1920×1080**：保持双栏，限制对话文字行宽，不把气泡拉成长条。
- **1440×900**：导航约 192px，主区域约 64:36；首屏必须可见输入和当前方案动作。
- **1366×768**：导航可收至 176px，缩减纵向留白；页面标题、输入区、确认按钮可达，列表与消息区域内部滚动。
- **窄屏**：导航紧凑化，详情切换为单栏；表格容器可横向滚动，整页不横向溢出。

以上是待实施规范，本轮未生成可运行前端，也未宣称这些尺寸已通过功能或视觉测试。

### 轻量反馈

- hover、focus 和颜色反馈约 140–180ms，不平移整个页面。
- 成功提示只反映后端已成功的动作；错误提示需要可读且可再次查阅。
- 键盘焦点清晰，图标按钮有名称，状态不仅依靠颜色区分。
- 遵守 `prefers-reduced-motion`，减少动态旋转或关闭非必要过渡。
- 技术详情按需展开；动效不能影响多轮消息阅读或操作确认。
